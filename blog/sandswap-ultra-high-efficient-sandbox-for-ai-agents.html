01The problem: isolation is priced per second — agents need it for milliseconds

LLM thinking — seconds to tens of seconds
measured floor: minimal-token tool round trip P95 1.06–1.18 s (no real reasoning) ◀ tool exec ≈ 2 ms (e.g. read a 1 MB file) — sandbox needed only here
  • Agents run generated, untrusted code → need hardware isolation
  • One sandbox per agent → isolation sits idle ~all the time
  • suspend/resume VM-per-request → 50+ ms latency overhead · extra snapshot/restore complexity
  • Amortize via session-level suspend/resume → deeper idling · overcommit → bursty load → CPU / memory contention

05Design principles: the contract every change must preserve

Deliberately independent of implementation, timer values, and file paths — the principles do not change as the code evolves.
P1
Everything persists
all meaningful state durable — resume after any failure
P2
Minimal E2E latency
gateway → sandlot → warden at the transport limit · no hot-path locks
P3
Minimal swap cost
swap-in on the critical path · swap-out in the background
P4 — SAFETY CORE
Never double-mounted
one SandFS on one microVM — at any instant, anywhere
P5
One sandlot, one gateway
a single outbound stream at any moment
P6
Sandlots stick, fail slow
switch gateway only after a bounded timeout
P7
Agents stick, fail slow
same time-gated failover — never flap
P8
Directories, not backends
any shared FS · any node serves any SandFS
together they guarantee: never double-mounted · resilient to failures · latency at the transport limit
weakening any one weakens the rest — all must hold

06SandFS: the agent's persistent filesystem — two modes

The microVM is the compute; the SandFS is the disk. Each agent owns one or more SandFS instances — everything it keeps lives here.

Flat — the build mode

chroot /mnt/rootfs — the whole volume, read-write
├─ template files → writable copy — /usr /etc /bin all persist
├─ /workspace     → plain dir in the volume (cwd)
├─ /home/agent    → plain dir in the volume
└─ /tmp           → plain dir in the volume — persists
  • apt / yum work — 10 ambient caps
  • seeded from local or OCI template
  • freeze → becomes a new template

Overlay — the serve mode

chroot /mnt/rootfs
├─ template files → read-only overlay (kernel-enforced)
├─ /workspace     → writable bind → volume
├─ /home/agent    → writable bind → volume
└─ /tmp           → fresh tmpfs — node-local, never shared
  • no upperdir/workdir → runs on any shared FS
  • layers extracted once, shared by all instances
  • zero capabilities — Strict profile
build in flat
→
save-as-template → OCI artifact
→
serve overlay ×N from one immutable base
  • Persists across swaps, VM recycle, node migration — pip / npm / files all survive
  • overlay SandFS: detach / attach template — swap the read-only base without losing agent work (workspace/ · home/ live in the volume)

10Guest kernel hardening: the kernel is the trust root under the swap

The kernel executes every in-VM clear — an implant would survive tenant switches. Every layer below cuts its probability or its reach.

Shrunk at build time — kernel/build.sh

  • Compiled out: USER_NS · TUN/VETH · KVM · BPF · IO_URING · USERFAULTFD · OVERLAY_FS · POSIX_MQUEUE · PROC_KCORE · ZSWAP · DEVMEM · x32 ABI …
  • Hardened in: UMIP · no legacy vsyscall · hardened usercopy · init_on_alloc
  • Backports: 17 upstream stable fixes on pinned v7.2.8 (cloud-hypervisor tag 2026-10-09) — net skb/UDP/IPv6 UAF & checksum · futex hash UAF · AIO recursion · netlink net_cookie
  • Gates: config check + nm symbol probe — a re-enabled symbol fails the build

Runtime posture

  • max_user_namespaces=0 — belt and braces
  • init_on_alloc default-on — zeroed allocations; init_on_free optional (fresh RAM already zero)
  • no vsock loopback transport → in-guest connect() = ENODEV
  • kernel + initramfs = pinned upstream artifact — guests can't influence boots

What agent code can ask of it — per-exec fence

  • seccomp deny 82: mount API · unshare/setns · ptrace class · bpf · perf · keyring · mqueue · modules · NUMA
  • sched / prlimit calls: self-target only (warden shares uid 0)
  • NO_NEW_PRIVS · caps ∅ (strict) / 10 (install)
  • balanced cBPF tree — log₂N comparisons, length unchanged

Blast radius — bounded by policy

  • compromise reads this VM's volumes only — never fleet-wide
  • affinity_vms 3 · max_distinct_agents 300 · max_mounts 10k · max_uses 100k
  • egress-only network · per-agent identity on every flow
  • high-security answer: dedicated cluster
  • TODO — make destroy-after-every-use practical: boot is only kernel + warden, inherently lightweight — once boot reaches the ms range (≈ swap-out cleanup), destroy-after-every-use drops the kernel-implant risk to its minimum

Why the overhead is this low — the design
  • 8 design principles (p.6) drive every hot-path choice — P2 latency at the transport limit · P3 swap-out in the background · P5–P7 stick, never flap
  • All work in memory — the main path never touches slow persistent storage: no boot · no storage op · no etcd I/O
