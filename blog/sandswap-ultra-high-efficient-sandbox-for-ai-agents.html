01The problem

Agent execution needs VM-grade isolation — but agents barely execute

The tension: strong isolation is expensive per second; an agent only needs it for milliseconds at a time.
  • AI agents run generated, untrusted code as tools (shell, file ops, installs) — shared-kernel containers are a weak boundary for this; you want a hardware-isolated VM.
  • But an agent's duty cycle is tiny: one turn = LLM thinking + a few milliseconds of execution. The measured floor on this stack — a minimal-token tool-call round trip, fast model, essentially no reasoning — is already P50 0.87–0.97 s; real agent turns with substantial prompts, outputs, and thinking run seconds to tens of seconds. Either way: ≥ 3 orders of magnitude above any sandbox segment (≤ 2.5 ms).
  • With one sandbox per agent, the VM does useful work < 1% of its lifetime — you pay for isolation 100% of the time and use it almost never.
  • Booting a fresh VM per request doesn't fix idle cost, and adds 100 ms+ of path latency plus snapshot/restore complexity.
  • The goal (and the two tough parts of this talk):
    • many agents time-share one strongly-isolated microVM, with swap overhead so small it vanishes next to think time — and at scale;
    • the swap itself must keep VM-grade isolation: zero residue between agents while dynamically mounting / unmounting filesystems into a live VM.

02Core idea

Swap the disk, not the machine — compute and storage decoupled

Sandswap redefines the microVM: it is pure compute. The agent's "disk" is a directory that is mounted in and out.
┌──────────────────────── microVM = compute only ─────────────────────────┐
│   minimized guest kernel + warden (PID 1), ~5 MB initramfs             │
│   deliberately EMPTY — no rootfs, nothing agent-specific inside        │
│                    ▲  one permanent virtio-fs device (never hot-plugged)
└────────────────────┼────────────────────────────────────────────────────┘
                     │  allowed_dirs = [ active agent's dir ]   swap ≈ 0.20 ms
┌────────────────────┴────────────────────────────────────────────────────┐
│  volumes/ = storage:  sf-a51f3c · sf-b7e2d9 · sf-cd08b4 · …             │
│  one directory per agent = its SandFS: the persistent rootfs           │
│  (local disk, or NFS / CephFS / Cloud FS — any shared filesystem)      │
└─────────────────────────────────────────────────────────────────────────┘
  • Attaching an agent = repoint the virtio-fs allowed_dirs filter (~0.20 ms) + a guest bind-mount swap. No boot, no copy, no snapshot / pause / resume ever touches the request path.
  • While agent A thinks (seconds), the same microVM serves B, C, …; when A's next call arrives, its SandFS is swapped back in. Everything an agent writes persists — the disk follows the agent, not the machine.
  • A boot costs seconds; a swap costs a filter update + a bind mount. That asymmetry is the entire economic argument.

03Architecture

Four components, three planes — built from scratch for the ms-scale swap

Almost the entire stack is purpose-built: VMM fork, guest kernel, PID 1, node daemon, gateway, DNS.
 AI agents ──HTTP :3000 / MCP──▶ GATEWAY ──gRPC stream (sandlot dials out)──▶ SANDLOT (1 per node)

                                 ownership · sticky lease · placement               │
                                 │  etcd + sandns (owner-aware DNS)         sandvmm — 1 VMM per microVM (KVM)
                                 │  multi-gateway only                       microVM: kernel + warden (PID 1)
                                 ▼                                                │
                        gateway never touches storage           virtio-fs device + allowed_dirs filter
                                                                          ▼
                                            volumes/ + templates/ — one dir per SandFS
                                            (plain directories; storage backend replaceable)
  • Gateway — entry point: authenticate, resolve sandfs_id, claim ownership, pick a node, open the lease. Storage-free by design.
  • Sandlot — per-node daemon: keeps the warm pool, swaps SandFS in/out, talks to each warden over vsock. No open ports — one outbound stream (NAT-friendly).
  • sandvmm — one trimmed Cloud-Hypervisor-fork process per microVM: KVM + the virtio-fs device and its filter; controlled over a Unix socket (rare, ms, off the hot path).
  • Warden — PID 1 inside every VM: mounts the SandFS, runs commands under caps/seccomp/memory limits, tears everything down at release.
  • Planes: control (human API + provisioning + etcd) · exec (agent traffic) · storage (prov-only writers). Distributed scale-out measures within noise of single-node — etcd sees zero writes per execution cycle in steady state.

04SandFS

SandFS — the agent's disk: one directory, two modes

The microVM is the compute; the SandFS is the disk. Everything the agent keeps lives here and persists across swaps.

Writesanything: /usr, /etc, pip, apt — all persists only workspace + home persist; rootfs read-only is kernel-enforced (host-side ro mount)

  • Overlay uses no upperdir / workdir — the read-only overlay works on any shared filesystem (NFS, CephFS, Cloud FS…); nothing stateful sits on the share.
  • Workflow: build in flat → freeze with save-as-template (an OCI artifact) → serve many overlay SandFS instances from one immutable base.

05Mechanism · swap-in

The cold path: filter swap + mount & exec in ONE vsock round trip

A cold request lands on an idle CLEAN VM from the warm pool — the request path contains no boot.
 agent          gateway                sandlot             sandvmm        warden (PID 1)
   │ POST /execute │                      │                   │                │
   ├──────────────▶│ auth · claim owner-  │                   │                │
   │               │ ship · pick node     │                   │                │
   │               │ · open sticky lease  │                   │                │
   │               ├─────────────────────▶│  bind an idle CLEAN pool VM        │
   │               │                      ├── vm.set-fs ─────▶│ allowed_dirs   │
   │               │                      │                   │ = [B]  ~0.2ms │
   │               │                      ├───── OP_MOUNT_AND_EXEC ──────────▶│ build mount
   │               │                      │                   │                │ stack, chroot,
   │               │                      │◀──────────── result + output ─────┤ fork + exec
   │◀──────────────┤◀─────────────────────┤                   │                │
   │  response     │                      │   pool refills asynchronously     │
  • Mount + exec combined into a single vsock RTT is the core latency trick — the warden builds the guest mount stack and spawns the first command in one operation (likewise mount_and_async_exec for background jobs).
  • Ordering invariants (both directions): the filter must be active before the guest mounts (the bind target must exist), and any stale mount must be gone before the filter swaps (A's files must be unnameable while B is attaching). Mounts never stack.
  • The egress identity binding is published before the mount — the first guest process can never emit un-attributed traffic.
  • Warm path: a follow-up call within the sticky window (default 100 ms; 1 ms in the benchmarks) skips everything — one OP_EXEC on a pooled connection: warm ≈ 0.96 ms, cold ≈ 2.3 ms (gateway E2E P95). Pool starvation fails fast (NO_AVAILABLE_SANDBOX) while the pool refills in the background.

06Mechanism · swap-out

The clearing chain: async, strictly ordered, fail-closed

Idle past the lease window (1 ms in benchmarks) → the unmount runs entirely off the response path, ≈3.1 ms P95, 100% under 5 ms even with 16 MB dirty pages.

Warden teardown — every step must precede the next

1mount gate (write lock): drain in-flight execs / file ops
2cgroup.kill — atomic SIGKILL of the whole agent process tree
3rule-A sweep — SIGKILL every live process above PID 1 (catches setsid stragglers that escape the cgroup)
4–5unmount child→parent: workspace/home, masked proc, /dev, busybox, then /mnt/rootfs — setup↔teardown symmetry, never MNT_DETACH
6drop_caches=3 — evict clean pagecache + dentries + inodes
7kernel-object sweep: SysV IPC, user keyring
8socket sweep: destroy dead-state TCP (sock_diag), flush neighbor table
9final-state gate: a zombie or D-state task above PID 1 fails the unmount
  • Only then does the sandlot clear the filter (allowed_dirs = []) and revoke the egress binding — filter clear after guest unmount, so teardown paths still resolve.
  • Fail-closed rule: if teardown cannot be proven complete — EBUSY, D-state process, unreachable warden — the VM is destroyed and replaced, never reused. A VM in an unknown state is a security question mark; a boot is just cost, off the request path.
  • No lazy detach: MNT_DETACH would leave a D-state process coexisting with the next agent — Sandswap fails loudly instead.
  • Recycling bounds reuse as hygiene (default max_uses 100k commands / max_mounts 10k attaches + memory pressure): isolation never depends on the VM being fresh, only on the swap being complete.
  • The result: the VM returns to the pool CLEAN in ~3 ms — while the agent it just served is still thinking.

07Isolation · boundary 1 of 2

VMM-side virtio-fs filter — what exists for the guest at all

All tenants live under one host directory tree; the filter makes each agent's world contain exactly one directory.
  • One rulebook: allowed_dirs holds exactly one directory — the active agent's. Not on the list = does not exist: a uniform ENOENT, so probing a sibling is indistinguishable from probing a name that was never there. Even the share-root listing is answered from the allow-list itself.
  • The active directory is presented under a per-generation random alias — real volume names never appear inside the guest, not even in /proc/self/mountinfo.
  • Names are exactly one path component — .., ., embedded /, empty, non-UTF-8 all refused; the validated type is the only form in code (a new opcode can't reintroduce the hole without failing to compile).
  • The host never follows a guest-chosen path: lookups via openat2(RESOLVE_IN_ROOT | RESOLVE_NO_MAGICLINKS) + O_NOFOLLOW, rooted at parent descriptors; inodes held as descriptors; reopens limited to regular files/dirs — planted symlinks and device nodes are inert.
  • Fail-closed everywhere: omitted allow-list = empty list (no "filter off" mode exists); share-root mutation gated above opcode dispatch, exhaustive over the enum; no vm.add-fs route; multi-fs configs refused.
  • Cache revocation: every set-fs clears the daemon's inode/handle tables and bumps revocation epochs — a request that began before the swap answers ESTALE; stale node ids die even in the A→B→A same-VM case.

08Isolation · boundary 2 of 2

Guest-side mount stack + per-exec confinement — what an agent can name

The filter decides what exists; the warden decides what can be named. Even a chroot escape is still confined by the filter.
  • Every exec: chroot + chdir into the bind-mounted SandFS — the process's namespace root is the active volume.
  • Hardened tree: nosuid,nodev share · read-only RAM-backed busybox · masked /proc (kcore/kallsyms/keys/kmsg covered, proc remounted ro) · minimal /dev, fresh size-capped /dev/shm · fresh tmpfs /tmp per attachment.
  • Per-exec sandbox: setsid · scrubbed env · NO_NEW_PRIVS · capability sets (strict: empty; install: 10) · seccomp deny of 82 syscalls (mount API, unshare/setns, ptrace/process_vm_*, bpf, keyring, mqueue, …) · RLIMIT_AS + per-agent memory.max = 70% VM RAM.
  • Warden self-defense: PID 1 (default signals inert, kill -9 1 does nothing), PR_SET_DUMPABLE=0, capability bounding set pre-dropped, CAP_SETPCAP never granted — the profile cannot be widened.

09The guarantee behind the swap

Zero residue: nothing of agent A survives into agent B

The hard part is not the mount — it is proving the machine is empty. Every leak vector has a named close; each layer is independently necessary.
Leak vectorClosed by
live processes / setsid stragglerscgroup.kill + rule-A sweep

  • Memory guarantee: no live process, no open descriptor, no cached page, no kernel object names A — that is the invariant; page scrubbing is unnecessary because no path from B's world can reach A's state.
  • Documented residues (by design): aggregate netns counters (traffic volume only); machine-reuse linkability (boot_id, source IP) — the egress identity attributes flows, it does not hide that one machine served both leases.
  • Underneath it all, the central invariant — one SandFS per microVM at any instant — enforced at four independent levels: cluster (ownership + placement CAS) · node (sandlot binds 1:1) · VM (warden MOUNT_GATE + mounted-volume identity, mismatch = refuse without executing) · guest (chroot).
  • Every behavior pinned by e2e suites: cross-tenant residue, hostile warden frames, share-root escape matrix, seccomp profiles — not by inspection.

10Security engineering at scale

Keeping the swap trustworthy when it spans host, VMM, and guest

Ultra-low latency usually means trusting your peers; Sandswap gets ms without trusting anyone.
  • Transport: the sandlot↔warden channel runs on kernel vhost-vsock — the whole data path lives in the kernel: zero VMEXIT per packet, no VMM context switch, no network stack. (Userspace virtio and virtio-net+TCP both add measurable cost.)
  • The unauthenticated warden port is closed three times: the guest kernel is built without vsock loopback (connect() to own CID → ENODEV) · vhost-vsock never relays guest→guest · the warden accepts host CID 2 only.
  • vsockguard — a BPF LSM on socket_connect: only the sandlot UID may dial the warden port; AF_VSOCK connect() goes through no device node, so DAC alone cannot close it.
  • The protocol assumes a hostile peer: mount_point pinned to exactly /mnt/rootfs (no shadowing cgroupfs) · volume-identity cross-check under the mount gate (mismatch → refuse without executing) · defensive frame parsing (a malformed frame closes the connection, never PID 1).
  • Compartmentalized host identities: sandvmm parses untrusted guest file requests, so it runs as its own UID with zero capabilities — a full VMM compromise reaches no warden, no storage write; the share root is traverse-only; volume names are HMAC-SHA256(seed, id) — 128-bit, seed never reaches the VMM, rotation re-keys all names.
  • Tenant network: one bridge, fail-closed nftables baseline — per-TAP anti-spoof · VM↔VM deny · guest→host default-deny; if the baseline can't install, the sandlot refuses to start.
  • Egress identity: an unforgeable per-attachment binding — published before mount, revoked at swap-out — so every flow is attributed to the right agent.

13Value & outlook

VM security at container economics — what this unlocks

Agents think in seconds; microVM reuse takes milliseconds. Every second of thinking is a second the VM serves someone else.
  • For agent platforms: every agent gets a hardware-isolated sandbox and a persistent workspace at container-like density — no more choosing between isolation and cost.
  • Persistence without servers: the SandFS follows the agent — pip, npm, apt, files, caches all survive swaps, VM recycling, and node migration; the agent never re-installs its world.
  • "Too fast" is a feature: the VM is typically swapped out between two reasoning steps. An agent that wants its next calls warm simply holds the VM with a background exec (sleep) — background jobs survive across calls, bounded by an absolute run-time cap.
  • Integration is boring by design: HTTP + MCP on one listener, API key from config, OCI-based templates, Prometheus metrics; bare metal today, Kubernetes via an unprivileged sandlot + privileged boxout sidecar (hot path needs zero privileges).
  • Beyond agents: the same time-sharing primitive extends to code interpreters, CI runners, and serverless sandboxes — anywhere strong isolation meets bursty, tiny workloads.
  • Open direction: shaping admission at the gateway to approach the ideal reuse capability under Poisson-distributed agent arrivals (documented as the next step).

14Takeaways

Sandswap in five sentences

  • Decouple compute from storage. The microVM is just a kernel + warden (PID 1); the agent's SandFS — a plain directory that is its rootfs — is mounted in and out.
  • Swap the filesystem, not the machine. A ~0.2 ms filter swap + mount & exec in one vsock RTT ⇒ 2.3 ms cold / 0.96 ms warm; swap-out (~3.1 ms) runs async off the response path.
  • Zero residue between agents — enforced at every layer, proven or the VM is destroyed: processes, caches, kernel objects, sockets, stale handles, memory paths.
  • No isolation traded for speed: stronger per-exec confinement than container defaults (NO_NEW_PRIVS, 82-syscall deny, VMM filter), VM-grade boundary throughout.
  • The economics: thinking in seconds vs swapping in milliseconds ⇒ 183 reuses/s per microVM, 64 agents per VM (measured), 10–100× lower environment cost.
